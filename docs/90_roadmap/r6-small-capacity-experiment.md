# Isolated reduced-capacity experiment

This branch is an experimental derivative of `bf9bb8f8f226f9742c55d3b1788819326716ebed` for issue #296. **Do not merge or distribute its runtime.** Its sole runtime alteration is `AgentLimits.Messages = 32` instead of the production value 64. Canonical limit identities consequently change. All continuation, state, token, tool and other resource limits retain their original values. Results cannot establish the adequacy of the production capacity or complete the historical C/D populations.

The test executable's `small-capacity` command admits up to twelve tools-growth stages and two post-reset stages, with the explicitly identified `small_capacity_growth_v2` stop rule. It reserves all fourteen possible child allocations before credential access. Each child uses the existing clean-source/build admission, private IPC, bounded real Agent/provider path, receipt checks and restricted-state service.

Successful growth stages are accepted and independently read back. After at least one accepted growth stage and a successful restoration of that predecessor, an observed capacity rejection must leave the selected predecessor readable. Only then are the remaining growth slots recorded as unattempted/not-needed and the preauthorized local state reset executed. Reset must verify absence before a new session accepts generation zero and another fresh process restores it. Exhaustion without capacity is insufficient. Other failures stop the experiment; no retry, summarization, fabricated history or capacity relocation occurs.

The report format is `apr.r6.small-capacity-experiment.v1`, with all fourteen slots, attempted evaluation outcomes, per-call usage and failure observations retained. It deliberately has no native C1 journal/pricing export and does not pass the ordinary economics report reader. Reference usage pricing is independently derived with the frozen tariff; unknown usage stays unknown. This is real-provider integration with local synthetic repository/state storage, not production GitHub Host publication or production-default capacity evidence.

Before any receipt can affect state or reset control flow, a private dense projection of observed calls is admitted by the existing canonical `UsageJournal` validator. It preserves original case identities and cumulative reservation/call semantics, but is never exported as a population or comparison. The full sparse schedule remains in the experimental report. Receipts that permit acceptance or capacity-triggered reset must also have known valid usage for every sent call.

Tests named `SmallCapacity...` verify successful measured rejection/reset/continuation, preservation and attribution of skipped slots, unrelated failure stops, and selection rejection before secret access. Twelve hostile-receipt cases cover unknown usage, invalid transport, invalid cache arithmetic and ordinal corruption at ordinary, capacity and post-reset boundaries. They first prove that the original envelope-only check accepts the mutated receipt, then prove that the strict parent check prevents acceptance or successor dispatch. The ordinary production baseline and its prior CI evidence remain separate from this deliberately altered experimental build.

The earlier 32-message population reached a SESSION construction boundary during replay entry and is preserved in `r6-small-capacity-32-result.md`. F48 stopped on a no-tool provider response and G48 exhausted the per-stage model-call budget during replay entry. Both failures are preserved. H returns to 32 messages and removes the unrelated replay-entry prerequisite; its growth chain still must accept a real predecessor and restore it before any capacity-triggered reset. Capacity may be the typed SESSION construction limit (including next-request capacity), or a measured over-limit Agent response. Neither permits automatic recovery from unrelated errors.
