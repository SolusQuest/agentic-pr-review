# R6 live tool-rejection diagnostic correction

[Bug #299](https://github.com/SolusQuest/agentic-pr-review/issues/299) follows the [#295 quality observation](r6-quality-observation.md). The #295 paid population remains unchanged: `cs-safe` failed with `agent_tool_arguments_invalid`, `repository-rule` failed with `tool_path_not_tracked`, and `ts-safe` completed with off-focus confirmed findings. The `ts-safe` safe-line comparison citation also met the scorer's mechanical prohibited-evidence rule; that mechanical classification does not erase the separate semantic off-focus failure. The original rejected provider arguments and paths were discarded. Neither historical tool failure can be assigned to an exact tool or argument from the retained report, and neither can be called a runtime defect from its code alone. V6 entry remains blocked; [#296](https://github.com/SolusQuest/agentic-pr-review/issues/296) is still gated.

The local opt-in evaluator now projects a known registry tool and a fixed rejection category when the same provider response and the Agent's actual failure code uniquely establish them. It mirrors the Agent's admission order: parse calls in order and stop at the first argument failure; only after that phase succeeds, preflight in order and stop at the first rejection. Attribution is `unknown` when the rejecting boundary cannot be established. For an argument rejection, the category distinguishes invalid JSON from a valid JSON value rejected by the tool contract. For a valid-but-untracked path, it records `path_not_tracked`. This diagnostic runs beside the Agent and does not change parsing, snapshot access or the failed outcome. Tool names outside the repository registry, raw arguments, paths, model text, reasoning, SESSION data and exception text are not retained in the report.

Keyless regression tests use the frozen V4 snapshot to reproduce both rejection boundaries before tool execution, including a valid sibling in the same batch. They exercise mixed-batch order, ambiguous calls, adversarial names and private-content canaries. The strict verifier now accepts only closed tool/category/code combinations, and the published #295 JSONL is checked by its original SHA-256 and strict round-trip read without adding new fields. A fresh paid diagnostic requires a separately reviewed correction head and finite plan; a two-case diagnostic by itself cannot satisfy the frozen five-case V6-entry rule. Any demonstrated runtime or scorer behavior defect belongs to a separate focused issue.
