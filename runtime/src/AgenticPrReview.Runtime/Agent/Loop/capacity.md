# R7 review count admission

`AgentLimits` defaults to 64 logical model calls, 512 budgeted tool calls per review and 16 tool calls per response. R7-C6 permits trusted Current configuration to select 1..128 logical calls; 128 is a separate hard ceiling and does not raise the 64 default or retained evaluator profiles. Tools execute serially in response order. These are independent upper bounds: token, deadline, request/response, message, continuation and tool-result byte limits can stop earlier. Current defaults to 900 seconds and permits a trusted lower timeout; retained profiles keep 300 seconds. See the [trusted review configuration contract](../../../../../docs/20_architecture/action-interface.md). No compaction or reset policy is added.

Each `AgentLoop.RunAsync` starts new per-review counters. Restored history is validated, including its per-message tool count, but its old calls are not charged as new review work. The current canonical limits identity includes the new counts; a selected-current plan with the former identity fails closed before chat. Historical evidence retains its original identities.

| Admission or operation                                                                                         | Logical model calls | Tool budget | Diagnostic tool calls |
| -------------------------------------------------------------------------------------------------------------- | ------------------- | ----------- | --------------------- |
| Core request rejection before entering chat                                                                    | 0                   | 0           | 0                     |
| Entering chat, including local projection/adapter/transport failure or a later invalid response                | 1                   | 0           | 0                     |
| Ordinary tool, charged before `ExecuteAsync`, including failed/throwing/cancelled execution or rejected result | Already charged     | 1           | 1                     |
| Sole prepared `finish_review`, charged before terminal semantic/evidence validation, whether valid or invalid  | Already charged     | 1           | 1                     |
| Terminal arguments rejected during preparation                                                                 | Already charged     | 0           | 0                     |
| Transactionally committed recovery member, including valid skipped siblings                                    | Already charged     | 1           | 0                     |
| Whole batch denied by per-response or remaining per-review count admission                                     | Already charged     | 0           | 0                     |

The complete response count is admitted before argument preparation, preflight or dispatch. An argument failure or recoverable preflight denial executes no member of that batch. Preflight can have run during recovery admission, but recovery never invokes `ExecuteAsync`. Its commit charges every original member, including valid siblings returned as `batch_not_executed`. Failed recovery staging commits no recovery budget or events. Ordinary and terminal calls produce `AgentToolCallEvent`; recovery produces separate recovery-call/error events. `AgentDiagnostic.ToolCalls` remains an attempted-execution counter, not the recovery-inclusive budget.

A completed review without recovery can execute 511 ordinary calls and then one `finish_review`. After 512 ordinary or recovered members, a terminal cannot bypass the budget. With eight slots left, a nine-member response is rejected wholly, including when its last argument is malformed. At defaults a terminal can finish on logical model call 64; an unfinished 64th response cannot cause a 65th invocation. Configured Current follows the same boundary at its selected limit, up to 128; accounting admits the same selected limit and rejects observations beyond the hard ceiling. Exhaustion and failures remain incomplete and ineligible for successful SESSION/publication.

Credential-free `AgentLoopTests` cover the exact counts, mixed recovery/execution, terminal preparation versus semantic rejection, failed execution charging, serial order, old identity refusal and earlier token/byte/time stops. `AgentToolResultBudgetTests` proves that 128 maximum-size 64 KiB results exhaust the independent 8 MiB result allowance before the 512-call ceiling. The existing `runtime/scripts/verify-agent-loop.sh all` gate executes framework and Native AOT production-loop proofs through synthetic provider requests and real snapshot reads. Its current R7 model-limit observation is 64 model calls / 64 tools / 64 requests; its tool-limit observation is 33 model calls / 512 tools / 33 requests. The denied final response dispatches no 513th tool. Current R7 SESSION goldens come from the deterministic producer; the original agent-loop and R4/R5/R6 fixtures remain historical.

The evaluator's independent eight-send child allocation remains eight. A ninth logical observation can record a final `budget_refused` without dispatch; the collector prevents ninth dispatch and a tenth observation. Receipt and report-observation admission accept only that exact refusal after eight completed sends. The unchanged campaign journal cannot treat a child-local refusal as exhaustion of its larger campaign allocation, so its parent retains unavailable journal/pricing export rather than inventing campaign reservations. A synthetic six-send run with 80 executed tools independently proves that current tool statistics cross the former 64-statistic pin while keeping portable completed-report admission. Tool statistics remain bounded by the actual dispatched response inventory, the per-response ceiling and the unchanged eight-send child scope.

## V3 managed review admission

The managed Host compositions use exact SolusAgent `0.1.0-internal.4`, context format `2/1` and the existing `cr1-solus-internal4-dev` runtime identity. V3 selects the following bounded review contract for managed qualification and D5 consumption. It does not select this route from the ordinary Action or change the Current/native limits above. The `.4` package has larger construction ceilings; those ceilings are not admitted APR configurations.

`SolusReviewCapacity` reads field presence from the authenticated policy bytes. Omitted `review` fields select these managed defaults. Explicit `maxModelCalls`, `timeoutSeconds`, `maxUncachedInputTokens`, `maxCachedInputTokens` and `maxOutputTokens` must be positive integral values within their managed maxima, and survive unchanged. A larger Current value, unknown field/profile, malformed value, duplicate field or unsupported selection is refused before affected new work. Native Current defaults remain 64 calls and 900 seconds; they are not silently reduced to managed values. No new repository configuration schema or selectable package/profile override is introduced.

Legal smaller selections feed the actual runtime call/work/dispatch bounds, duration, observed thresholds and accounting allowances. APR independently enforces the selected uncached and cached balances. The runtime's combined input allowance is `min(65,536, uncached + cached)`, an additional total-input constraint. A selected output allowance below 1,024, or combined input allowance below 8,192, cannot fund the first reservation and visibly refuses without a physical send. An individual input axis below 8,192 does not alone imply zero sends: a valid first measurement can exhaust that independent APR axis. Nothing raises a small selection or invents measured consumption.

The managed duration bounds current runtime execution. Host preparation, recovery and publication retain their existing separate overall envelope; an explicit repository timeout also constrains that Host envelope. Elapsed Host time can shorten remaining execution authority, without changing the selected maximum.

The immutable R5 C#/TypeScript defect/safe and repository-rule corpus supplies useful fresh and subsequent reviews through the actual Host, current snapshot tools, candidate validation, capture and durable successor acceptance. V3 adds six-tool/six-call work, complete-batch refusal, correction, escaped result growth, larger deterministic usage and consecutive useful successors through the first observed refusal. Passing two reviews is a minimum workload witness, not an indefinite-history promise. Every accepted successor retains previous records, tool members, candidate bookkeeping and round usage; current instructions may be replaced as specified by Solus. Historical observations do not become current evidence. No history is dropped, compacted, truncated, reset or replaced with fresh execution to fit another review.

Record accounting reports ordinary `Records`, candidate `Episodes`/`Submissions`, recovery actions and tool members separately. Candidate reservation checks include ordinary records plus episodes, submissions, applicable recovery actions and prospective growth; members have additional independent admission checks and are not blindly counted twice. Actual encoded checkpoint bytes differ from variable retention and prospective receipt/episode/correction reservations. The real-runtime diagnostic probes isolate cumulative attempts, candidate record admission and the serializer/reservation boundary without copying the Solus codec. Their reduced or larger diagnostic configurations are not additional admitted product profiles, and cannot establish reachability of shadowed product maxima.

The gate records each attempt's classified inputs, logical bytes, full response allowance, tool result counts/bytes, actual HTTP messages/roles and wire bytes, plus known current token usage, reservations/allowances and historical/current attempts. Synthetic usage is engineering evidence, not a live token, quality or cost measurement. A coarse runtime stop is reported as observed; identifying a particular binding axis requires direct evidence or an isolated probe.

Capacity refusal can occur before a new source claim, or after a claim and some current work. The accepted predecessor, consumed claim and newly accepted successor are distinct states. Incomplete work never becomes a clean review or accepted successor; consumed claims are not refunded. Known-commit recovery and bounded pending cleanup retain their prior truth without a provider key or new provider work, even when new review data would be invalid for a new execution. Changed policy can reject an incompatible lineage before new-input validation. No dedicated error-code priority overrides those recovery rules.

D5 must consume the exact qualified pin/profile and its actual receipt, including the observed useful envelope and limitations. Any later pin/profile change invalidates this capacity evidence and requires affected fresh/restored, state-transition and package qualification again. No new upstream package is presumed necessary from constructor ceilings or historical `.1` failures alone.
